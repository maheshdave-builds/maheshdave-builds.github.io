A merchant asked for a simple thing: every time a product's price or status changes, push the SKU to the PIM. The first implementation was a plugin on ProductRepositoryInterface::save(). It worked in REST tests, passed QA, and then quietly missed every change the catalog team made through CSV import and the "Update attributes" mass action. Nobody noticed for three weeks.

The root problem is that "a product was saved" is not one event in Magento. There are at least four write paths, and each one exposes a different hook. Before choosing a plugin, observer, or preference, you need to know which paths your requirement actually covers.

The four write paths

PathWhat runsHook that sees it
REST / service codeProductRepository::save() → resource model saveRepository plugin, catalog_product_save_after
Admin product formAdmin save controller → model/resource savecatalog_product_save_after (repository plugin only if your version's controller calls the repository)
System → Import (CSV)Direct multi-row SQL in Magento\CatalogImportExport\Model\Import\Productcatalog_product_import_bunch_save_after
Mass "Update attributes"Magento\Catalog\Model\Product\Action::updateAttributes()catalog_product_attribute_update_before

The model event catalog_product_save_after is dispatched by the abstract model's save cycle, so it fires whenever a product model is persisted through the resource model, including through the repository. That makes it a wider net than a repository plugin. Import and mass update never instantiate a product model per row, so neither hook sees them. That is by design: those paths are fast precisely because they skip the model layer.

So the decision is not "plugin or observer". It is "one observer for model saves, plus one hook per bulk path, all feeding the same service".

Why not a preference or a plugin on the resource model

A preference on Magento\Catalog\Model\ResourceModel\Product would catch model saves but still miss import and mass update, and it conflicts with any other extension that prefers the same class. A plugin on the resource model's save() has the same coverage as the observer with more coupling. The observer wins on coverage per line of code, and the bulk paths need their own handling anyway because they deliver IDs or SKUs, not models.

The module

The recorder writes changed SKUs into a small table. A cron or consumer can drain that table toward the PIM later; that part is out of scope here. Recording synchronously into a table keeps the save path cheap and survives PIM outages.

The SKU is the primary key on purpose. Ten saves of the same product between two export runs collapse into one row, which is the behavior the PIM wants.

app/code/MaheshDave/ProductAudit/Model/ChangeRecorder.php

resource->getConnection();
        $table = $this->resource->getTableName(self::TABLE);

        foreach (array_chunk($skus, self::CHUNK) as $chunk) {
            $rows = array_map(
                static fn (string $sku): array => ['sku' => $sku, 'source' => $source],
                $chunk
            );
            $connection->insertOnDuplicate($table, $rows, ['source']);
        }
    }

    /**
     * @param int[] $productIds
     */
    public function recordByIds(array $productIds, string $source): void
    {
        $productIds = array_values(array_unique(array_map('intval', $productIds)));
        if ($productIds === []) {
            return;
        }

        $connection = $this->resource->getConnection();
        foreach (array_chunk($productIds, self::CHUNK) as $chunk) {
            $select = $connection->select()
                ->from($this->resource->getTableName('catalog_product_entity'), ['sku'])
                ->where('entity_id IN (?)', $chunk);
            $this->record($connection->fetchCol($select), $source);
        }
    }
}

insertOnDuplicate() with an explicit update column list means a repeat change only rewrites source; changed_at refreshes through on_update.

Wiring the three hooks

app/code/MaheshDave/ProductAudit/etc/events.xml

This file lives in global etc/, not etc/adminhtml/. Import can run from cron or CLI-based tooling, and REST runs in the webapi_rest area; an admin-only file would miss both.

app/code/MaheshDave/ProductAudit/Observer/ProductSaveAfter.php

getEvent()->getProduct();
        if (!$product instanceof ProductInterface) {
            return;
        }

        if ($product->isObjectNew() || $this->hasWatchedChange($product)) {
            $this->recorder->record([(string) $product->getSku()], 'model_save');
        }
    }

    private function hasWatchedChange(ProductInterface $product): bool
    {
        foreach (self::WATCHED as $code) {
            if ($product->dataHasChangedFor($code)) {
                return true;
            }
        }

        return false;
    }
}

dataHasChangedFor() compares against the original data loaded with the model. A product saved without loading first (a bare model with only an ID and one attribute) reports every set field as changed, which errs toward recording too much. That is the right failure direction for a sync.

app/code/MaheshDave/ProductAudit/Observer/ImportBunchSaveAfter.php

getEvent()->getBunch();
        $skus = [];
        foreach ($bunch as $row) {
            if (!empty($row['sku'])) {
                $skus[] = (string) $row['sku'];
            }
        }

        $this->recorder->record($skus, 'import');
    }
}

The import adapter dispatches this event once per bunch with the raw rows. Rows that only touch an attribute the PIM ignores will still be recorded; filtering by column here is possible, but import rows only contain the columns present in the CSV, so you would check array_key_exists() against your watched codes.

app/code/MaheshDave/ProductAudit/Observer/MassAttributeUpdate.php

getEvent();
        $productIds = (array) $event->getData('product_ids');
        $attributes = array_keys((array) $event->getData('attributes_data'));

        if (array_intersect($attributes, ['price', 'status', 'name', 'special_price']) === []) {
            return;
        }

        $this->recorder->recordByIds($productIds, 'mass_update');
    }
}

This is a before event, so a failed update would still leave rows behind. For a sync queue that is acceptable: the exporter sends current values, and an unchanged product produces a harmless no-op on the PIM side. If your downstream cannot tolerate that, record in a plugin on afterUpdateAttributes() of Magento\Catalog\Model\Product\Action instead.

On large stores the admin mass update may run asynchronously through the product_action_attribute.update consumer. The event still fires, just inside the consumer process, which is one more reason the observer config belongs in global scope.

Paths this still does not cover

  • Direct SQL from other extensions or ERP connectors that write catalog_product_entity_decimal themselves.
  • Scheduled changes in Adobe Commerce (staging) that become active at a time boundary rather than through a save.
  • Price changes produced by catalog price rules, which live in the index, not on the product.

If any of those matter, the honest answer is a database-level approach: an mview subscription on the attribute tables feeding a custom indexer, which captures writes regardless of who made them.

SELECT sku, source, changed_at
FROM maheshdave_product_change
ORDER BY changed_at DESC
LIMIT 10;

Expected: model_save for REST and the admin form, import after a CSV import of a few SKUs, and mass_update after "Update attributes" on a price or status change. If the admin form produces no row, check that the attribute you edited is in WATCHED before suspecting the event.
