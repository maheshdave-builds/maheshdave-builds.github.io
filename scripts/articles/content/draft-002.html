The usual extension attribute tutorial adds an afterGet() plugin, loads the value, and sets it. Then someone copies the same per-item lookup into afterGetList(), the ERP polls /V1/orders with a page size of 200, and every poll costs 200 extra queries. The response still looks correct, which is why this survives code review.

This article builds an erp_reference extension attribute on orders, stored in its own table, and loads it for list calls with one query per page.

Where the value lives

Putting a custom column on sales_order is tempting, but it makes the order table wider for every query in the system and it ties your schema to a core table's lifecycle. A side table keyed by order_id keeps the data owned by the module and lets you drop the module cleanly.

Declaring the attribute

app/code/MaheshDave/OrderErp/etc/extension_attributes.xml

After setup:di:compile, the generated Magento\Sales\Api\Data\OrderExtension gets getErpReference() and setErpReference(). Those methods do not exist until generation runs, so a stale generated/ folder shows up as "Call to undefined method" rather than as a missing value.

The XSD also supports a <join> child that asks the extension attributes join processor to add the column to collection queries. It only helps when the repository's getList() passes its collection through JoinProcessorInterface::process(), and that varies by repository and version. A plugin is explicit and behaves the same everywhere, so that is what I use for anything a downstream system depends on.

            $result[(int) $orderId] = (string) $reference;
        }

        return $result;
    }

    public function afterGetList(
        OrderRepositoryInterface $subject,
        OrderSearchResultInterface $result
    ): OrderSearchResultInterface {
        $this->apply($result->getItems());

        return $result;
    }

    /**
     * @param OrderInterface[] $orders
     */
    private function apply(array $orders): void
    {
        $ids = [];
        foreach ($orders as $order) {
            $ids[] = (int) $order->getEntityId();
        }

        $references = $this->reader->getByOrderIds($ids);

        foreach ($orders as $order) {
            $extension = $order->getExtensionAttributes() ?? $this->extensionFactory->create();
            $extension->setErpReference($references[(int) $order->getEntityId()] ?? null);
            $order->setExtensionAttributes($extension);
        }
    }
}

Two details that bite in practice. First, getExtensionAttributes() can return null on orders built outside the repository, so the factory fallback is not optional. Second, the order repository caches loaded orders in an internal registry by ID; afterGet() runs on every call regardless, so the lookup repeats for repeated get() calls in the same request. If a hot path calls get() on the same order repeatedly, memoize in the reader.

Writing the value

Reading is half the contract. If the ERP writes back through POST /V1/orders with the extension attribute set, nothing persists it unless you add a save plugin. Most integrations I have seen write the reference through a dedicated endpoint instead, which keeps the order save path untouched. Whichever you choose, do not let the attribute appear writable in the API schema without a persistence path behind it; clients will send it and assume it stuck.

Proving the query count

Seed a reference for a known order:

INSERT INTO maheshdave_order_erp (order_id, erp_reference)
SELECT entity_id, CONCAT('SO-', increment_id) FROM sales_order ORDER BY entity_id DESC LIMIT 50;

Then request a page:

: > var/debug/db.log
curl -s -G "https://example.test/rest/V1/orders" \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  --data-urlencode "searchCriteria[pageSize]=50" \
  | jq '.items[] | {increment_id, erp: .extension_attributes.erp_reference}' | head -20
grep -c "maheshdave_order_erp" var/debug/db.log

The grep should return 1 for the whole page. If it returns 50, something in the stack is calling get() per item after getList() (third-party plugins on the order repository do this more often than you would expect), and the fix is in that plugin, not yours.
