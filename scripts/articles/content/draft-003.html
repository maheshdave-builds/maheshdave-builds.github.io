When an ERP sync fails at 2 a.m., the first question is "what did we send and what came back?" On many projects the answer is buried in var/log/system.log between cache warnings, payment debug lines, and two other integrations that also log to the default channel. The second question, "why did it hang for 60 seconds?", usually ends at a shared HTTP client with no timeout.

Both problems have the same fix, and it does not need a single new PHP class: virtual types in di.xml.

What a virtual type actually is

A virtual type is a named set of constructor arguments for an existing class. The object manager creates an instance of the real class with those arguments whenever the virtual name is requested. There is no generated class file and no inheritance; you cannot instanceof a virtual type and you cannot type-hint one. That is the point: the consuming class depends on Psr\Log\LoggerInterface, and configuration decides which logger it gets.

The alternative people reach for is a subclass of Magento\Framework\Logger\Handler\Base with a $fileName property. It works, but it is a PHP file per integration that exists only to hold a string.

The consuming class

The client below knows nothing about which log file or timeout it uses. It is written exactly as it would be with the default logger.

app/code/MaheshDave/ErpConnector/Model/ErpClient.php


     * @throws LocalizedException
     */
    public function ping(): array
    {
        $baseUrl = rtrim((string) $this->scopeConfig->getValue(self::XML_PATH_BASE_URL), '/');
        if ($baseUrl === '') {
            throw new LocalizedException(__('ERP base URL is not configured.'));
        }

        $started = microtime(true);
        try {
            $response = $this->httpClient->request('GET', $baseUrl . '/health');
        } catch (GuzzleException $e) {
            $this->logger->error('ERP ping failed', [
                'url' => $baseUrl . '/health',
                'error' => $e->getMessage(),
                'elapsed_ms' => (int) ((microtime(true) - $started) * 1000),
            ]);
            throw new LocalizedException(__('ERP is unreachable: %1', $e->getMessage()), $e);
        }

        $result = [
            'status' => $response->getStatusCode(),
            'elapsed_ms' => (int) ((microtime(true) - $started) * 1000),
        ];
        $this->logger->info('ERP ping', $result);

        return $result;
    }
}

Guzzle is a dependency of magento/framework in 2.4.x, so GuzzleHttp\ClientInterface is available without adding a package. Depending on the interface keeps the class testable with a mock handler.

A few things worth knowing about this file:

  • fileName is relative to the Magento root and starts with a slash, the same convention core handlers use for /var/log/system.log.
  • Magento\Framework\Logger\Monolog is Magento's Monolog subclass. Passing it a fresh handlers array replaces the default handlers, so these entries no longer appear in system.log or debug.log. Usually that is what you want. If ops alerting watches exception.log, add the core handler Magento\Framework\Logger\Handler\Exception as a second item.
  • The Guzzle constructor parameter is literally named $config, which is why the argument name is config. Argument names in di.xml must match parameter names, not types.
  • Virtual type names look like class names by convention only. Namespacing them under the module avoids collisions; two modules defining ErpLogger would silently override each other.

A second integration is configuration only

When the shipping carrier integration arrives, it gets its own handler, logger, and client by repeating the pattern with different names and a 30-second timeout for label generation. The carrier class does not change, and neither does the ERP config. That isolation is what makes virtual types worth it: tuning one integration's timeouts can no longer break another.

The tradeoff is discoverability. A developer reading ErpClient sees LoggerInterface and assumes system.log. I add the log file name to the module's README and keep all virtual types for a module in its global di.xml, never scattered across area files, so there is one place to look.

Exercising it

A small command makes the wiring testable from a shell.

app/code/MaheshDave/ErpConnector/Console/Command/PingCommand.php

setName('maheshdave:erp:ping');
        $this->setDescription('Call the ERP health endpoint using the connector client');
    }

    protected function execute(InputInterface $input, OutputInterface $output): int
    {
        try {
            $result = $this->erpClient->ping();
        } catch (LocalizedException $e) {
            $output->writeln('' . $e->getMessage() . '');
            return Command::FAILURE;
        }

        $output->writeln(sprintf('HTTP %d in %d ms', $result['status'], $result['elapsed_ms']));

        return Command::SUCCESS;
    }
}

Constructor injection in a console command means the client and its whole dependency graph are built when bin/magento lists commands. For a light class like this that is fine. For commands with expensive dependencies, inject a Proxy (MaheshDave\ErpConnector\Model\ErpClient\Proxy in di.xml) so listing commands stays fast.

Register the command, alongside the virtual types, in the same di.xml:


    
        
            MaheshDave\ErpConnector\Console\Command\PingCommand

The module has no system.xml, so bin/magento config:set would reject the path. Set the base URL in app/etc/env.php, which is where an environment-specific endpoint belongs anyway:

'system' => [
    'default' => [
        'maheshdave_erp' => [
            'connection' => [
                'base_url' => 'https://erp-sandbox.example.test',
            ],
        ],
    ],
],

bin/magento module:enable MaheshDave_ErpConnector
bin/magento setup:upgrade
bin/magento setup:di:compile
bin/magento maheshdave:erp:ping
tail -n 5 var/log/erp_connector.log

A healthy run prints something like HTTP 200 in 84 ms and writes a line tagged erp_connector.INFO: ERP ping. Point the base URL at a blackholed address (for example a non-routable IP) and the command should fail after about three seconds with the connect timeout, not after PHP's default socket timeout. That three-second failure is the real test that the client virtual type was injected.

If the log line lands in system.log instead, the logger argument did not apply. The usual cause is a typo in the argument name, which the object manager ignores silently, or a stale generated/metadata in production mode.
