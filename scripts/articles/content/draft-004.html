Two bug reports that look unrelated have the same cause. In the first, a developer renamed ref_code to external_reference in db_schema.xml; after deployment the column existed, but every value was gone. In the second, a developer deleted an obsolete column from db_schema.xml, ran setup:upgrade, and the column was still there a month later.

Declarative schema compares the XML to the live database and generates the difference. It cannot see intent. A rename looks exactly like "drop one column, add another", and a removal is only applied if Magento knows your module created that column in the first place. That second piece of knowledge lives in etc/db_schema_whitelist.json.

What the whitelist does

The whitelist records every table, column, index, and constraint the module has declared. During setup:upgrade, Magento only drops elements that appear in the whitelist but no longer appear in db_schema.xml. Anything not in the whitelist is assumed to belong to someone else (a legacy install script, another module, a DBA) and is left alone.

That explains both reports:

  • The removed column was never in the whitelist because the developer never regenerated it, so Magento refused to drop it. Correct, conservative behavior.
  • The renamed column was in the whitelist. The new XML no longer mentioned ref_code, so it was dropped, and external_reference was created empty.

The whitelist must be committed and regenerated whenever the schema changes:

bin/magento setup:db-declaration:generate-whitelist --module-name=MaheshDave_Loyalty

It is additive: generating it again after a removal keeps the old entry, which is exactly what lets the drop happen on the next upgrade. Do not hand-edit it to "clean up" removed names.

Renaming a column without losing data

The column element accepts an onCreate attribute. migrateDataFrom(old_name) tells Magento to copy values from the old column when it creates the new one, before the old one is dropped.

Then regenerate the whitelist so it contains external_reference as well as the old names:

app/code/MaheshDave/Loyalty/etc/db_schema_whitelist.json (generated)

{
    "maheshdave_loyalty_member": {
        "column": {
            "member_id": true,
            "customer_id": true,
            "ref_code": true,
            "legacy_tier": true,
            "external_reference": true
        },
        "constraint": {
            "PRIMARY": true,
            "MAHESHDAVE_LOYALTY_MEMBER_CUSTOMER_ID": true
        }
    }
}

Leave onCreate in place after release. It only acts when the target column does not exist yet, so it is a no-op on databases that already migrated and still correct on any environment that lags behind, such as a developer restoring an old dump.

Renaming a whole table works the same way at table level with onCreate="migrateDataFromAnotherTable(old_table_name)". For very large tables this is a full copy inside the upgrade, so measure it on a production-sized dump before trusting it with a maintenance window.

Removing something another module declared

You cannot drop another module's column by omitting it, because it is not in your whitelist. The supported route is to redeclare the element in your own db_schema.xml with disabled="true". That applies to columns, indexes, constraints, and whole tables. Use it sparingly: disabling a core index to speed up imports, for example, is something you will have to defend during every upgrade.

See the SQL before running it

Two flags on setup:upgrade make schema changes reviewable and reversible:

bin/magento setup:upgrade --dry-run=1 --keep-generated
grep -n "maheshdave_loyalty_member" var/log/dry-run-installation.log

Dry run writes the DDL it would execute to var/log/dry-run-installation.log without touching the database. For the rename above, you should see an ALTER TABLE adding external_reference, an UPDATE copying from ref_code, and the drops of ref_code and legacy_tier. If the UPDATE is missing, the onCreate did not parse; check for a typo in the old column name.

bin/magento setup:upgrade --safe-mode=1

Safe mode dumps data from columns and tables about to be dropped into CSV files under var/declarative_dumps_csv/. If a drop turns out to be wrong, bin/magento setup:upgrade --data-restore=1 restores from those dumps after you put the element back in the XML. It is not a backup strategy, but it is a cheap safety net for a release that removes columns.

Things that still need a data patch

Declarative schema moves data only for the rename cases above. Changing a column type from varchar to int, splitting one column into two, or backfilling a new non-nullable column from logic are data problems. Declare the schema, then write a data patch that transforms values, and make the new column nullable until the patch has run everywhere. Trying to do it in one step produces a failed ALTER on the first row that does not convert.

Checking the result

SHOW COLUMNS FROM maheshdave_loyalty_member;
SELECT COUNT(*) AS total, COUNT(external_reference) AS with_reference FROM maheshdave_loyalty_member;

Compare with_reference against the count of non-null ref_code values you recorded before the deploy. Recording that number is the step people skip, and it is the only way to prove the migration copied everything.
