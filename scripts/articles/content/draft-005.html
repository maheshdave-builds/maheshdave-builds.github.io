A category listing needed "approved review count" as a sortable value. The first implementation recalculated a summary table from a nightly cron with a TRUNCATE and a big INSERT ... SELECT. At 20,000 products nobody cared. At 400,000 products with marketplaces feeding reviews all day, the table was wrong for most of the day and the rebuild locked it for minutes.

Magento already has the machinery for "recalculate only what changed": an indexer with an mview subscription. Triggers on the source table write changed IDs into a changelog, and the indexer_update_all_views cron job hands those IDs to your indexer. You write the calculation once, scoped to a list of IDs, and get both full and partial reindex.

The pieces

  • indexer.xml registers the indexer so indexer:status, indexer:reindex, and the admin Index Management grid know about it.
  • mview.xml declares which tables to watch and which column identifies the entity. Magento creates the changelog table and the triggers when the indexer is switched to "Update by Schedule".
  • One class implementing both Magento\Framework\Indexer\ActionInterface (full, list, row) and Magento\Framework\Mview\ActionInterface (changelog batch).

entity_column is the column whose value is written into the changelog. For product reviews, review.entity_pk_value holds the product ID, so the changelog will contain product IDs directly. Choosing this column well is the main design decision in any mview setup: if the source table does not carry your entity ID, you either subscribe to a different table or translate IDs inside execute().
Status changes (pending → approved) update the same review row, so the trigger covers moderation too. Deleting a review fires the delete trigger with the old row's value, which is exactly what we need to decrement the count.
The indexer class
app/code/MaheshDave/ReviewIndex/Model/Indexer/ReviewCount.php
resource->getConnection();
        $connection->delete($this->resource->getTableName(self::INDEX_TABLE));
        $this->insertCounts($connection, null);
    }

    public function executeList(array $ids)
    {
        $this->reindexIds($ids);
    }

    public function executeRow($id)
    {
        $this->reindexIds([$id]);
    }

    public function execute($ids)
    {
        $this->reindexIds($ids);
    }

    /**
     * @param int[]|string[] $ids
     */
    private function reindexIds(array $ids): void
    {
        $ids = array_values(array_unique(array_map('intval', $ids)));
        if ($ids === []) {
            return;
        }

        $connection = $this->resource->getConnection();
        $table = $this->resource->getTableName(self::INDEX_TABLE);

        foreach (array_chunk($ids, self::BATCH) as $chunk) {
            $connection->beginTransaction();
            try {
                $connection->delete($table, ['product_id IN (?)' => $chunk]);
                $this->insertCounts($connection, $chunk);
                $connection->commit();
            } catch (\Throwable $e) {
                $connection->rollBack();
                throw $e;
            }
        }
    }

    /**
     * @param int[]|null $productIds null means all products
     */
    private function insertCounts(AdapterInterface $connection, ?array $productIds): void
    {
        $select = $connection->select()
            ->from(['r' => $this->resource->getTableName('review')], [])
            ->join(
                ['re' => $this->resource->getTableName('review_entity')],
                're.entity_id = r.entity_id',
                []
            )
            ->where('re.entity_code = ?', Review::ENTITY_PRODUCT_CODE)
            ->where('r.status_id = ?', Review::STATUS_APPROVED)
            ->group('r.entity_pk_value')
            ->columns([
                'product_id' => 'r.entity_pk_value',
                'approved_count' => new \Zend_Db_Expr('COUNT(*)'),
            ]);

        if ($productIds !== null) {
            $select->where('r.entity_pk_value IN (?)', $productIds);
        }

        $connection->query(
            $connection->insertFromSelect(
                $select,
                $this->resource->getTableName(self::INDEX_TABLE),
                ['product_id', 'approved_count']
            )
        );
    }
}

Products whose last approved review was removed simply disappear from the table after the delete, and readers treat a missing row as zero. That is cheaper than writing zeros for 400,000 products on every full reindex.
The full reindex here deletes and rebuilds in place, so readers briefly see an empty table. For this data that is acceptable. If it is not for yours, core uses a replica-table swap through Magento\Framework\Indexer\Table\StrategyInterface; it adds complexity worth paying only when readers cannot tolerate a gap.
\Zend_Db_Expr is still what Magento\Framework\DB\Select expects for expressions in 2.4.x. Projects on 2.4.6+ may see it aliased through laminas packages; the class name used by core code remains Zend_Db_Expr.
Turning it on
bin/magento module:enable MaheshDave_ReviewIndex
bin/magento setup:upgrade
bin/magento setup:di:compile
bin/magento indexer:set-mode schedule maheshdave_review_count
bin/magento indexer:reindex maheshdave_review_count
bin/magento indexer:status maheshdave_review_count

Switching to schedule mode is what creates the changelog table maheshdave_review_count_cl and the triggers on review. In "Update on Save" mode nothing is subscribed, and since this indexer has no save hooks of its own, it would only change on full reindex. If you want realtime mode to work too, add an observer on review_save_after that calls executeRow(); for review volume I would not bother.
Watching a partial reindex happen
Approve a pending review in admin (or update one directly on a dev database), then:
SELECT * FROM maheshdave_review_count_cl ORDER BY version_id DESC LIMIT 5;
SHOW TRIGGERS LIKE 'review';

The changelog should hold the product ID with a new version_id. Then process the backlog the way production cron would:
bin/magento cron:run --group=index
bin/magento indexer:status maheshdave_review_count

SELECT * FROM maheshdave_review_count_idx WHERE product_id = 42;
SELECT version_id FROM mview_state WHERE view_id = 'maheshdave_review_count';

The count should reflect the approval, and mview_state.version_id should have advanced to the changelog's latest version. If the changelog grows but the state never moves, the index cron group is not running; that is a cron problem, not an indexer problem, and indexer:status will show the backlog as "N in backlog" on 2.4.x.
