An order export that only runs when RabbitMQ is up will not run on a developer laptop, so people test it for the first time on staging. The inverse, a consumer hardcoded to the MySQL queue, sits idle in production after the broker is installed because nothing publishes to it. Magento already picks the transport at deploy time. The module should define the topic once and leave the connection unset.

Connection resolution, as documented for communication.xml, queue_publisher.xml, queue_topology.xml, and queue_consumer.xml: if you omit connection, Magento uses amqp when env.php contains an AMQP config, stomp when ActiveMQ Artemis is configured (2.4.5+), and db otherwise. Pinning connection="db" disables that. Pinning both and toggling disabled also works, but then every environment change is a code change. Omitting the attribute is the version I ship.

What gets published

The message is the order id as a string. A data interface is worth it when the payload has several fields; an id is enough here because the consumer reloads the order and therefore sees the current state rather than a snapshot that went stale in the queue.

Throwing from process() rejects the message and Magento retries it. Catching every exception and returning makes a poison message look successful. If the ERP is down, throw. If the order id is nonsense, log and return so it does not retry forever. That split belongs in this method once the real client exists; the handler above is the boundary, and a missing order throws NoSuchEntityException, which is the retry case I accept because a replica lag of a few seconds is normal right after placement.

Where the transport is chosen

Local app/etc/env.php has no queue/amqp key, so this topic uses the queue and queue_message tables. Production has the broker block Magento writes when you configure RabbitMQ (host, port, user, password, virtualhost). Do not commit that block. After changing it, bin/magento setup:upgrade recreates the queue topology for the resolved connection.

One explicit override is legitimate: a consumer that must stay on MySQL even in production, because it is a small control message and you do not want the broker as a dependency. Set connection="db" on that consumer and on its exchange only. Do not set it on this export.

Publish from a one-off integration test or by placing an order through a plugin on OrderRepositoryInterface::save that calls ExportPublisher only when the order is new. Then:

SELECT id, topic_name, body FROM queue_message ORDER BY id DESC LIMIT 5;

On a laptop this returns a row with topic maheshdave.order.export and the order id as the body, and the consumer log line follows. On production the same SQL returns nothing, because the row is in RabbitMQ; rabbitmqctl list_queues name messages (or the managed equivalent) shows maheshdave.order.export. If production still writes queue_message, the AMQP block is missing or the config cache was warmed before env.php changed.
