A category page asks GraphQL for 24 products and a custom backorder_note field. The resolver loads a row by SKU. The page is correct and the database log shows 24 identical selects. GraphQL calls the field resolver once per item; Magento does not batch those calls for you unless the field is backed by a data loader you wrote.

The approach that holds up: the field resolver implements BatchResolverInterface, so Magento hands it every product on the page in one call. It loads those SKUs with a single IN (?) query and answers each item from the map.

Schema

This is a field on ProductInterface, not a new root query. Root queries you invent are outside the cacheable query list Adobe documents (products, categories, route, and the others on that page). A field on products rides the query that is already cacheable.

    private ?array $notes = null;

    public function __construct(
        private readonly ResourceConnection $resource
    ) {

    /**
     * @param string[] $skus
     */
    public function warm(array $skus): void
    {
        if ($this->notes !== null) {
            return;
        }
        $skus = array_values(array_unique(array_filter($skus)));
        $this->notes = [];
        if ($skus === []) {
            return;
        }
        $connection = $this->resource->getConnection();
        $select = $connection->select()
            ->from($this->resource->getTableName('maheshdave_backorder_note'), ['sku', 'note'])
            ->where('sku IN (?)', $skus);
        foreach ($connection->fetchPairs($select) as $sku => $note) {
            $this->notes[(string) $sku] = (string) $note;
        }
    }

    public function get(string $sku): ?string
    {
        return $this->notes[$sku] ?? null;
    }
}

The loader is a normal injectable, so Magento gives you one instance per request. That is the memoization. Do not store this map on a singleton you registered yourself; the shared instance would leak the previous request's SKUs across PHP-FPM workers only if you made it static, and a static property here would survive for the life of the worker and serve another customer's catalog. Keep it on the object.

Magento 2.4.7 (and the 2.4 line that includes BatchResolverInterface) will call resolve() once with every parent product when the resolver implements that interface instead of ResolverInterface. Confirmed against lib/internal/Magento/Framework/GraphQl/Query/Resolver/BatchResolverInterface.php on the 2.4.7 tag. A class that implements the single-item interface never sees the rest of the page.

BatchResponse stores values in an SplObjectStorage keyed by the request object. You must pass the same $request instance you were given; a copy will not match and findResponseFor() throws when Magento reads the result back. getValue() is the parent array the product resolver already built, which includes sku for a ProductInterface field. It is null when the field is resolved without a parent, and the resolver returns null rather than querying.
