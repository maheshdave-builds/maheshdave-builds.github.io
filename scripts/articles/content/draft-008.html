The storefront team reported a Fastly hit rate near zero on /graphql while category HTML sat at 90%. The query was products, which Magento does cache. The client was sending it as an HTTP POST with the query in the body. Fastly's Commerce VCL only considers caching a GraphQL request when it is a GET whose query string contains query=. A POST is a pass, every time, and no Magento header will change that.

What Magento will cache

Adobe's GraphQL caching documentation lists the queries that participate: products, categories, categoryList, cmsBlocks, cmsPage, route, storeConfig, urlResolver, and a short set of metadata queries. It explicitly does not cache cart, customer, customerOrders, wishlist, or customer payment tokens. One uncached root field in an otherwise cacheable document bypasses the cache for the whole request. A persisted "page" query that also asks for customer { firstname } is a permanent miss, and it looks like a Fastly bug.

A custom root query you add in schema.graphqls is not on that list. I do not add one when the data can be a field of products or categories. Those parents already carry cache tags (X-Magento-Tags in developer mode), so a price change purges the response. A new root query would need its own cache identity wiring, and that wiring is not a documented one-liner; treat a claim that @cache on an arbitrary query "just works" as something to verify on your patch level before you depend on it.

The cache id is not the URL

From 2.4.4, Magento returns X-Magento-Cache-Id on GraphQL GET and POST responses. The value is a SHA-256 of store id, currency, whether the customer is logged in, customer group, customer tax rate, and a salt. Sending that value back on the next request lets Fastly (module 1.2.160 or later, with the current VCL uploaded) serve a different object per context without varying on the Authorization bearer or on cookies. The header is for Varnish and Fastly. The built-in file FPC does not honor it. Mutations do not return it.

Guest traffic does not need the header for a hit. Logged-in traffic does, because a bearer token would otherwise make every key unique. The client has to store the header from the response and attach it to the following GET. Most Apollo setups never do this, because they POST and never read response headers.

X-Magento-Vary is not used for GraphQL. Store and currency come from the Store and Content-Currency headers. A query with no Store header is cached under the default store, then replayed to a request for another store view if you vary only on the URL. I send Store on every request, including the ones I expect to hit.

A request that can hit

curl -sD - -o /dev/null -G "https://example.test/graphql" \
  -H "Store: default" \
  -H "Content-Currency: USD" \
  --data-urlencode 'query=query{products(filter:{sku:{eq:"24-MB01"}}){items{sku name}}}'

First response: X-Magento-Cache-Debug: MISS when the app is in developer mode, and Fastly's X-Cache contains MISS. Second identical request: HIT. The same call with -X POST and a JSON body stays on MISS or PASS. If the second GET is still a miss, check three things in order: the Fastly module is at least 1.2.160 and the VCL has been uploaded, the query string actually contains the query (a persisted-query POST will not), and the document does not include a field from the uncached list.

For a logged-in client, read X-Magento-Cache-Id from the first response and send it next time:

CACHE_ID=$(curl -sD - -o /dev/null -G "https://example.test/graphql" \
  -H "Store: default" -H "Authorization: Bearer $CUSTOMER_TOKEN" \
  --data-urlencode 'query=query{products(search:"bag"){items{sku}}}' \
  | awk -F': ' 'tolower($1)=="x-magento-cache-id"{gsub("\r","",$2); print $2}')
curl -sD - -o /dev/null -G "https://example.test/graphql" \
  -H "Store: default" -H "Authorization: Bearer $CUSTOMER_TOKEN" \
  -H "X-Magento-Cache-Id: $CACHE_ID" \
  --data-urlencode 'query=query{products(search:"bag"){items{sku}}}'

The customer token still has to be valid; the cache id only stops Fastly from treating that token as part of the cache key. Group and tax rate are already inside the hash. If you add another factor through idFactorProviders on Magento\GraphQlCache\Model\CacheId\CacheIdCalculator, every distinct value multiplies the number of objects. I have used that for a B2B shared-catalog id, and the hit rate fell until the catalog count was small enough that the extra dimension paid for itself. Measure the cardinality before you add a factor, not after the Fastly bill moves.
