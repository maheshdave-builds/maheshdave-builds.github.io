The first admin screen for export status selected every row in maheshdave_order_export_status, json-encoded it, and let Knockout filter. At a few hundred orders it felt instant. At the volume the ERP actually produces, the HTML request spent longer in PHP than the grid spent rendering, and a "filter by failed" still transferred the successes. Magento's listing component already sends filters and page size to mui/index/render. The work is to point that pipeline at the table, not to build a second one.

The name has to match in three places

The data provider name, the js_config provider string, and the collections item in di.xml are one identifier. A typo does not throw. The grid renders with an empty collection and a successful HTTP 200, which is why this survives QA on a fixture of zero rows.

app/code/MaheshDave/OrderExport/Model/ResourceModel/Status/Grid/Collection.php

SearchResult takes $mainTable and $resourceModel in its constructor. Setting them in di.xml keeps the collection class empty, which is what you want: grid behavior (filters, order, page size) is applied by Magento\Framework\View\Element\UiComponent\DataProvider\DataProvider onto this collection. A collection that calls load() inside _initSelect() defeats the paging, because the limit is applied too late or not at all if you already fetched.

The layout handle is {frontName}_{controller}_{action}. The file name is that handle. A file named after the UI component never loads, and the page is an empty admin content area with a 200.

Confirm the SQL, not the pixels

bin/magento cache:flush
bin/magento dev:query-log:enable

Open admin/maheshdave_export/status/index, filter State equals failed. In var/debug/db.log the select on maheshdave_order_export_status contains WHERE state = 'failed' and a LIMIT. If the filter changes the rows on screen but the SQL has no WHERE, the filtering is happening in the browser and this listing is not actually wired. Turn the query log off when you are done.
