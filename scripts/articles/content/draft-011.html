"Retry export" on the status grid worked for the five orders QA selected. Operations selected the whole failed filter, about two thousand rows, and the admin tab spun until Fastly returned 503. The controller was calling the ERP inside the request. The browser, PHP-FPM, and Fastly all have timeouts shorter than that loop. The mass action's job is to record the selection and return a message. A consumer does the work.

The listing item

Inside maheshdave_export_status_listing.xml, as a sibling of columns:


    
        
            
            retry
            
            basic

actionType>basic posts the selected ids. A confirmation modal is available and I use it when the action is destructive; a retry is not, and a modal on a retry trains people to click through it.

The controller publishes

app/code/MaheshDave/OrderExport/Controller/Adminhtml/Status/Retry.php

filter->getCollection($this->collectionFactory->create());
        $count = 0;
        foreach ($collection->getAllIds() as $incrementId) {
            $this->publisher->publish(self::TOPIC, (string) $incrementId);
            $count++;
        }
        $this->messageManager->addSuccessMessage(__('%1 orders queued for export.', $count));

        return $this->resultFactory->create(ResultFactory::TYPE_REDIRECT)->setPath('maheshdave_export/status/index');
    }
}

Filter applies the selection, or the "select all across pages" excluded-id set, onto the collection. Reading $this->getRequest()->getParam('selected') yourself misses the excluded-ids case and retries the wrong page. getAllIds() returns the primary key. Publishing inside the loop is acceptable at a few thousand ids because each publish is an insert, not an HTTP call. If the selection can hit hundreds of thousands, write one bulk insert into queue_message or chunk through a single message that contains the filter, not the ids. I have not needed that for an operational retry.

The consumer is the one from the queue article, maheshdave.order.export, and it must tolerate a duplicate id. A merchant will click the action twice. insertOnDuplicate on the status row, and an ERP call keyed by increment id, make the second run a no-op. If the ERP call is not idempotent, do not queue it this way.

There is no CSRF token to add by hand. Admin POST actions go through Magento's form key via the UI component. A raw fetch you add later has to send form_key. This one does not.

What you should see

Select two failed rows, run Retry export. The page comes back in well under a second with "2 orders queued for export." Then:

SELECT topic_name, body FROM queue_message ORDER BY id DESC LIMIT 5;

Two bodies, the two increment ids, topic maheshdave.order.export. Start the consumer with --max-messages=2 and the ERP log (or the handler log) shows those two orders and nothing else. If the admin request itself logs ERP traffic, the controller is still doing the work and the queue is decoration.
