The integration asked for orders with status processing, page size 50. The response was 50 orders of every status. The repository was fine. The criteria object that arrived had no filter groups. The builder had been asked to create() twice, and create() clears the builder so the next caller does not inherit the previous request's filters. The second call, which only set the page size, was the object that got passed.

One create, at the end

SortOrderBuilder::create() also resets. Build the sort, then the criteria, and do not call create() on the criteria builder to "peek". Builders are mutable and, in the default DI setup, not a fresh object per class if someone registered them as shared in a way that leaks; Magento creates them as shared unless you inject a proxy or a factory. create() clearing state is what makes a shared builder safe. If you stash the builder and add filters across requests in a long-running consumer, call create() or you will AND the new filters with the previous message's filters. I inject the builder and finish with one create() per message.

AND versus OR

Two addFilter calls on the same builder are ANDed. They become one filter group. Orders that are processing AND in store 1 is what the code above asks for. Orders that are processing OR pending need two groups:

$processing = $this->filterBuilder->setField('status')->setValue('processing')->create();
$pending = $this->filterBuilder->setField('status')->setValue('pending')->create();
$criteria = $this->searchCriteriaBuilder
    ->addFilters([$processing, $pending])
    ->setPageSize(50)
    ->create();

addFilters (plural) puts those filters in one group, and a group is OR. A later addFilter starts another group, which is AND across groups. Mixing them because the names look similar is how a "failed or exported, for this website" query drops the website. FilterBuilder is Magento\Framework\Api\FilterBuilder. It also resets on create().

getItems() is keyed by entity id. count($items) is the page, not the total. The total is getTotalCount() on the search result. Clients that stop when the page contains fewer than 50 rows are fine; clients that stop when count($items) === 0 are also fine. Clients that compare count($items) to getTotalCount() and expect them to match have confused the page with the whole result.

Look at the criteria, not the JSON

Log $criteria->getFilterGroups() before getList while reproducing. An empty array means the builder was reset or the filters were never added. A single group with two filters is the AND. Two groups means an OR plus something else. Then call the REST method the integration uses and compare total_count with:

SELECT COUNT(*) FROM sales_order WHERE status = 'processing' AND store_id = 1;

Those numbers match when the criteria survived. If the SQL count is 40 and total_count is the size of sales_order, the filter group is empty and the page size is the only part that arrived.
