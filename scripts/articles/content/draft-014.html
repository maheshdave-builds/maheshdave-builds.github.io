Product pages updated within a minute of a price import. Category pages, which list those products, still showed the old price and the old position until someone purged the whole site. The import and the indexer were doing what they were written to do: they registered product cache tags. A category page in full-page cache is tagged with the category, cat_c_{id}, and Fastly keeps serving it until that tag is purged. Soft-purging a product tag does not select the category object.

Magento\Catalog\Model\Category::CACHE_TAG is cat_c. Magento\Catalog\Model\Product::CACHE_TAG is cat_p. The page-cache identifier is {tag}_{id}. Fastly's Commerce module purges the tags Magento hands it through the cache-invalidation flow. If the tag was never registered, there is nothing to purge, and a "soft purge" setting is not the thing that is wrong.

Register the category ids the reindex actually changed

Plug in after the category-product indexer processes a list of product ids, resolve the categories those products are in, and register those category tags. Then dispatch clean_cache_by_tags, which is the event the cache-invalidation layer listens on.

    /**
     * @param int[] $productIds
     */
    private function purgeForProducts(array $productIds): void
    {
        $productIds = array_values(array_unique(array_map('intval', $productIds)));
        if ($productIds === []) {
            return;
        }
        $connection = $this->resource->getConnection();
        $select = $connection->select()
            ->from($this->resource->getTableName('catalog_category_product'), ['category_id'])
            ->where('product_id IN (?)', $productIds)
            ->distinct(true);
        $categoryIds = array_map('intval', $connection->fetchCol($select));
        if ($categoryIds === []) {
            return;
        }
        $this->cacheContext->registerEntities(Category::CACHE_TAG, $categoryIds);
        $this->eventManager->dispatch('clean_cache_by_tags', ['object' => $this->cacheContext]);
    }
}

This plugin runs for the partial list. A full executeFull on a large catalog would resolve every category and purge almost the whole FPC, which is the flush you were trying not to do, only slower. I do not attach it to executeFull. A nightly full reindex can purge cat_c once, deliberately, in a maintenance window. Schedule mode ("Update by Schedule") calls the list path with the changelog ids, which is the path this covers.

Anchor categories and categories that include the product through a rule rather than catalog_category_product are not in that select. If the stale page is a visual-merchandiser category, the row may live in the index table catalog_category_product_index instead. Read the store-scoped index table for that case, and expect one row per store, so distinct still matters.

Change a product in that category, run bin/magento cron:run --group=index if the indexer is on schedule, and request the category again. The first request after the purge is a miss and shows the new price. If the tags header contains only cat_p_* and store tags, the category block is not adding its identity, and purging cat_c will never select that object. That is a block identity problem, not an indexer problem.
