The block rendered the promo during the miss and then became anonymous bytes inside the page. Full-page cache purges by tag. A block that does not declare identities adds no tag, so a save of the promo has nothing to purge.

On save, the abstract model already asks for identities when the model implements the interface, and the page-cache layer collects them. Calling clean_cache_by_tags yourself on top of that double-purges and is how a busy admin save turns into a stampede. I only dispatch that event when the write path does not go through the model, which is the same situation as a bulk SQL update.

The block has to actually be rendered inside the cached page. A block created in a controller and echoed, or filled via AJAX after load, is not part of the FPC document and its identities are never recorded. Layout XML is what puts it in the hole punch list Magento walks:

cacheable="false" on this block does purge nothing faster. It disables caching for the entire page, which hides the bug by never storing the page. Leave it cacheable and give it a tag.

See the tag, change the row, see it go

With developer mode on, the category response includes X-Magento-Tags containing maheshdave_promo_14. If the tag is absent, the block was not rendered on that request (wrong handle, empty promo_id). Save the promo in admin. The next category request is a miss and the banner text matches the save. A hit with the old text and the tag present means the save path did not purge: the admin form is writing SQL without the model. Move that write onto the repository, or register Promo::CACHE_TAG with the saved id and dispatch clean_cache_by_tags there.
