The New Relic overview for this service was dominated by WebTransaction/Action/index and a lump of CLI time called something like OtherTransaction/php/bin/magento. A 40-second order export ran every five minutes inside cron and never appeared as its own transaction. Apdex and error rate were storefront numbers. The export could fail all night and the only signal was a queue depth someone happened to query.

The PHP agent names web transactions from the framework when the framework calls the agent. Magento's web front does that. bin/magento cron:run does not name each job, and a consumer process lives until maxMessages, so one process name covers a hundred different messages. Set the name at the start of the job. The functions are newrelic_name_transaction and newrelic_add_custom_parameter, provided by the New Relic PHP extension. Guard them with function_exists so local DDEV, which has no agent, does not throw.

app/code/MaheshDave/DevTools/Model/NewRelic/Transaction.php

 $value) {
            if (is_scalar($value)) {
                newrelic_add_custom_parameter((string) $key, $value);
            }
        }
    }
}

Call it before the work, not after. A name set at the end still helps the next segment, but the time already recorded sits on the previous name.

$this->transaction->name('cron/maheshdave_order_export', ['website_id' => $websiteId]);

Inside a consumer, name it once per message and include the topic, not the order id. An order id as a transaction name creates one unique name per order and New Relic drops them as cardinality noise. The order id belongs in a custom parameter only if you accept that it is high cardinality; I put the increment id in the log line and keep the parameter set to the store id.

$this->transaction->name('consumer/maheshdave.order.export', ['store_id' => (int) $order->getStoreId()]);

The module is MaheshDave_DevTools because this is diagnostic instrumentation, not order-export business logic. The export module depends on DevTools or, if you refuse that dependency, duplicate the ten-line class. I depend on it. A consumer that catches exceptions and does not rethrow looks successful to the agent. Call newrelic_notice_error with the exception in that catch, or the error rate stays flat while the log fills up. That function is also part of the agent and needs the same function_exists check.

What changes in the UI

After one cron cycle with the agent installed, Transaction shows cron/maheshdave_order_export with a duration you can compare to the schedule. The consumer name appears as its own row instead of being folded into bin/magento. Filter request.uri or transaction name LIKE 'cron/%' and the storefront disappears. If nothing new shows up, the CLI binary is a different PHP than the one with the extension: php -m | grep newrelic using the same binary cron uses. A web SAPI with the extension and a CLI SAPI without it is the usual split.
