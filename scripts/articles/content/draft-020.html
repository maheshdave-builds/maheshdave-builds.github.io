The export-status grid filtered by state = 'failed' and ordered by updated_at. New Relic's slow SQL list showed that select at about two seconds once the table passed a few hundred thousand rows. The database tab is not proof. It is a candidate. I copy the SQL, run EXPLAIN on a replica, and only then add an index. An index for a query that is slow because it returns 100,000 rows does nothing but slow down the writes.

EXPLAIN SELECT increment_id, state, updated_at
FROM maheshdave_order_export_status
WHERE state = 'failed'
ORDER BY updated_at DESC
LIMIT 20;

type ALL and rows equal to the table size means there is no usable index. Using filesort in Extra on top of that is the sort of the whole filtered set. The index that matches this plan is (state, updated_at). state alone filters but still filesorts. updated_at alone does not satisfy the WHERE, so MySQL ignores it for this query.

Declare it

An ALTER TABLE on production, or an index added in phpMyAdmin, disappears the next time someone rebuilds an environment from db_schema.xml, and declarative schema may also drop it if the whitelist says the module owns the table and the XML does not mention the index. Put the index in the schema and regenerate the whitelist.

app/code/MaheshDave/OrderExport/etc/db_schema.xml gains, inside the existing table node:


    
    


bin/magento setup:db-declaration:generate-whitelist --module-name=MaheshDave_OrderExport
bin/magento setup:upgrade --dry-run=1

The dry-run log should show an ADD INDEX and nothing else. If it shows column drops, stop. The whitelist or the XML does not match the table that is live. On a table this size the alter is the risk: it can lock writes for the duration on MySQL versions and settings that do not allow ALGORITHM=INPLACE for that index. Read the statement in the dry-run log. Run it in the window you would run any other alter, not as a side effect of a code deploy you described as "no schema change".

After setup:upgrade:

EXPLAIN SELECT increment_id, state, updated_at
FROM maheshdave_order_export_status
WHERE state = 'failed'
ORDER BY updated_at DESC
LIMIT 20;

Do not add a second index on updated_at alone "just in case". The grid's WHERE is state first. A leftover single-column index makes the optimizer's choice depend on statistics, and the plan you explained today is not the plan you get after the next analyze. One composite index that matches the query is the change.
