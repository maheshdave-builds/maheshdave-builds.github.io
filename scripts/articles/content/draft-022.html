The ERP sent a shipment notification, Magento created the shipment, and the connection dropped before the 200 reached the ERP. The ERP retried. Magento created a second shipment for the same items and the order went to a state the warehouse could not reconcile. Timeouts and retries are the normal behavior of the caller. The receiver that is not idempotent is the defect.

The header I require is X-Event-Id, which the ERP already generates, and X-Signature, an HMAC-SHA256 of the raw body using a shared secret stored in Magento config (encrypted, not in the repo). I reject the request before any write if either is missing or the signature does not match.

CSRF validation has to be skipped because the caller is not a browser with a form key. That is safe only because the signature check is mandatory. A controller that returns true from validateForCsrf and does not verify a signature is an open endpoint.

insertOnDuplicate with an empty update list still reports a duplicate key as an affected-row count of 0 when the row exists and no column changes. I rely on a primary key on event_id. Insert the event row before creating the shipment. If shipment creation throws, leave the row and return 500 only if you delete the row in the same failure path; otherwise a retry hits the duplicate branch and the shipment is never created. The version I run stores status on the event row (accepted, then processed) and the duplicate branch returns the stored result after retrying the shipment step when status is still accepted. The snippet above is the gate. The shipment call, using Magento\Sales\Api\ShipOrderInterface, sits between the insert and the response, and a unique key on the shipment's ERP document number inside that call is the second lock.

db_schema.xml for maheshdave_webhook_event has event_id varchar 64 as the primary key, payload as mediumtext, and received_at timestamp default current. Route the controller at erpwebhook/shipment/notify in etc/frontend/routes.xml only if you want a storefront URL; I put it on webapi.xml as an anonymous route when the signature is the authorization, and I do not also leave a frontend route up.
