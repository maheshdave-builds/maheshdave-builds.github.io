Calling the ERP from checkout_submit_all_after couples the customer's request to a system you do not control. When the ERP is slow, checkout is slow. When the PHP process is killed after the order commits and before the HTTP call returns, the order exists and the ERP never hears about it. There is no row you can query to find those. An outbox row written next to the order is the list of work, and it survives the crash because it commits with the order.

Magento does not enlist your HTTP call in the database transaction. It will enlist an insert you run on the same connection before the order save completes, if you do the insert in sales_order_save_after while the transaction is still open. Observers on that event run inside the save. A queue publish does not. I insert the outbox row in the observer and publish only after a successful response is not required; a cron publishes rows that are still pending, so a publish that never happened is recovered.

app/code/MaheshDave/OrderExport/Observer/WriteOutbox.php

getEvent()->getOrder();
        if (!$order instanceof OrderInterface || !$order->getEntityId()) {
            return;
        }
        if (!$order->getOrigData('entity_id')) {
            $this->resource->getConnection()->insertOnDuplicate(
                $this->resource->getTableName('maheshdave_order_outbox'),
                ['order_id' => (int) $order->getEntityId(), 'status' => 'pending'],
                []
            );
        }
    }
}

getOrigData('entity_id') is empty on the insert and populated on later saves, so a status change does not enqueue the order again. events.xml listens to sales_order_save_after. The table's primary key is order_id, which makes a double-fired event harmless.

app/code/MaheshDave/OrderExport/Cron/PublishOutbox.php

resource->getConnection();
        $table = $this->resource->getTableName('maheshdave_order_outbox');
        $select = $connection->select()->from($table, ['order_id'])->where('status = ?', 'pending')->limit(100);
        foreach ($connection->fetchCol($select) as $orderId) {
            $this->publisher->publish('maheshdave.order.export', (string) $orderId);
            $connection->update($table, ['status' => 'queued'], ['order_id = ?' => (int) $orderId, 'status = ?' => 'pending']);
        }
    }
}

The update is conditional on status = pending so two cron processes cannot both publish the same row and both mark it. They can both publish if they read before either updates. The consumer must tolerate a duplicate order id, which it should anyway. If you need exactly-once publish, lock the row with SELECT ... FOR UPDATE in a transaction. I have not needed it at this volume; the consumer's idempotency is the real guarantee, and the outbox is the guarantee that the message is not lost.

Mark the row sent in the consumer after the ERP accepts it, and failed with a last error after the final retry. A row that stays queued and never becomes sent is a consumer problem. A row that stays pending is a cron problem. Those are different pages in an incident, which is the reason for the two statuses.

Kill the process on purpose

Place an order. SELECT * FROM maheshdave_order_outbox WHERE order_id = ... shows pending even if you then kill the PHP-FPM worker. Run the cron. The row moves to queued and queue_message has the id. Run the consumer. The row moves to sent. If you only look at the ERP and not at this table, you will miss the orders sitting in failed, which is the queue you actually have to drain.
