The feed had one price per website. The importer called ProductRepositoryInterface::save() with the price set and no store context. Magento was in the admin store (store id 0). Website-scoped price attributes store the default value in that case, and every website that did not have an override showed the US price. The EU website override was never written. The API response looked successful.

A price attribute with website scope is stored in the attribute's value table with store_id 0 for the default and with the store id of each store view when overridden. Saving under the wrong store writes a row you did not intend, and the fallback logic then hides the bug: the website with no row shows default, so US looks correct and EU looks "not updated".

app/code/MaheshDave/PriceFeed/Model/WebsitePriceWriter.php

storeManager->getStore($storeCode);
        $this->emulation->startEnvironmentEmulation((int) $store->getId());
        try {
            $product = $this->productRepository->get($sku, true, (int) $store->getId(), true);
            $product->setPrice($price);
            $this->productRepository->save($product);
        } catch (NoSuchEntityException $e) {
            throw $e;
        } finally {
            $this->emulation->stopEnvironmentEmulation();
        }
    }
}

The third argument of get() is the store id used to load values. Edit mode true skips the flat in-memory cache of a product loaded for another store earlier in the same process. A long-running importer that does not pass the store id, and does not force reload, will save the first website's product over and over with a new price. I have shipped that bug. The finally stops emulation even when save throws, so the next SKU is not stuck in the EU store.

Emulation changes the current store for the whole process, including any plugin on save that calls getValue without a scope. That is what you want here and it is also why this code must not run inside a web request that still has to render another store. Run it from CLI. Do not call it from a storefront controller.

After the write, the price index is stale until catalog_product_price runs. The value you read back from the EAV table can be right while the storefront is wrong. Reindex that one indexer, or wait for schedule mode. Checking only the storefront is how this gets reported as "the save didn't work" an hour before cron.

The row that proves it

SELECT s.code, c.value
FROM catalog_product_entity_decimal c
JOIN eav_attribute a ON a.attribute_id = c.attribute_id AND a.attribute_code = 'price'
JOIN store s ON s.store_id = c.store_id
JOIN catalog_product_entity p ON p.entity_id = c.entity_id
WHERE p.sku = '24-MB01';

You want a row whose store code is the EU store view, not only admin / store id 0. One row at store id 0 means the writer never left the admin store. Then open the EU storefront only after the price indexer has run, or you will compare an indexed price with an EAV price and reopen the ticket.
