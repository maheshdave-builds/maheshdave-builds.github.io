Duplicate orders, same quote, two increment ids, a few hundred milliseconds apart. The payment gateway showed one capture. The second order had no capture and a processing status that nothing could fulfill. The audit of plugins on PaymentInformationManagementInterface::savePaymentInformationAndPlaceOrder found an around plugin whose job was to log how long placement took. The happy path called $proceed, logged, and returned. A catch block called $proceed again because the author thought the first call had not counted after an exception. Exceptions from $proceed mean the call happened. A second call places a second order if the first one committed, and throws a quote-is-not-active error if it did not. Both happened, depending on timing.

Logging does not need around

after runs only if the method returned. You lose the duration of failures. That is a bad trade if you are building a metric, and it is the right trade if a mistake in the metric code can place an order. I log duration from the New Relic transaction instead, and the plugin that remains is after for a result I need to change. When I do write around, $proceed is called once, on one line, and the result is what I return.

app/code/MaheshDave/DevTools/Plugin/PlaceOrderTiming.php

logger->error('place order failed', [
                'cart_id' => $cartId,
                'ms' => (int) ((microtime(true) - $started) * 1000),
                'error' => $e->getMessage(),
            ]);
            throw $e;
        }
        $this->logger->info('place order finished', [
            'cart_id' => $cartId,
            'order_id' => $orderId,
            'ms' => (int) ((microtime(true) - $started) * 1000),
        ]);

        return $orderId;
    }
}

One $proceed. The catch logs and rethrows the same exception. It does not call the gateway again. Returning a new exception instead of throwing the original one drops the stack and can convert a LocalizedException the storefront knows how to print into a generic 500. Rethrow.

around is the plugin type that can skip the original method by not calling $proceed. That is the only reason I reach for it: a feature flag that returns a cached result, or a guard that throws before any side effect. An around that always calls $proceed and only adds behavior before or after is an before plus an after, and those cannot run the original method twice. Code review on this class is the question "how many times is $proceed invoked on each path", including paths added in a later pull request. I have rejected a "retry" branch here. Retry of place order belongs in the client, with a new idempotency key, not in a plugin that shares the same quote.
